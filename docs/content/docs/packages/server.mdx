# @homeslate/server

The homeslate Hono API: display CRUD, the public kiosk route, the Google OAuth
routes, and the calendar, commute, weather-alerts, and Home Assistant proxies.
Requires **Node 22.13+** (`node:sqlite` through `@homeslate/adapters`).

## Install

```bash
pnpm add @homeslate/server
```

## Usage

```ts
import { startHomeslateServer } from "@homeslate/server";

await startHomeslateServer({
  dataDir: "./data",
  publicBaseUrl: "http://homeslate.lan",
  google: { clientId: process.env.GOOGLE_CLIENT_ID, clientSecret: process.env.GOOGLE_CLIENT_SECRET },
  openRouteServiceApiKey: process.env.OPENROUTESERVICE_API_KEY,
  homeAssistant: {
    baseUrl: process.env.HOMEASSISTANT_BASE_URL,
    token: process.env.HOMEASSISTANT_TOKEN,
  },
  seedEmptyDisplay: true,
  onListen: ({ port }) => console.log(`homeslate API on http://127.0.0.1:${port}`),
});
```

`startHomeslateServer` binds `127.0.0.1:8787` by default. Resolves once the
server is listening.

## Mounting it yourself

`createHomeslateServer(options)` returns the Hono app, so you can add routes,
test it, or run it on another runtime:

```ts
import { Hono } from "hono";
import { createHomeslateServer } from "@homeslate/server";

const app = new Hono();
app.route("/", createHomeslateServer({ dataDir: "./data" }));
app.get("/api/solar", (c) => c.json({ watts: 4200 }));
```

## Options

| Option | Default | Notes |
| --- | --- | --- |
| `dataDir` | — | sqlite database + Google token files |
| `publicBaseUrl` | `http://127.0.0.1:8787` | builds the OAuth redirect URI |
| `google` | unset | `{ clientId, clientSecret }`; empty disables calendar |
| `homeAssistant` | unset | `{ baseUrl, token }` for a LAN Home Assistant, or `{ transport }` for a [relay](/docs/packages/relay); empty disables HA widgets |
| `openRouteServiceApiKey` | unset | enables `/api/commute` |
| `accountId` | `"local"` | single-tenant display owner |
| `displayStore` | sqlite in `dataDir` | any `DisplayStore` |
| `tokenStore` | file store in `dataDir` | any `TokenStore` |
| `port` / `hostname` | `8787` / `127.0.0.1` | `startHomeslateServer` only |
| `seedEmptyDisplay` | `false` | `startHomeslateServer` only |

### Bind address

`startHomeslateServer` binds `127.0.0.1` by default, which is right when the
API runs on the same host as your reverse proxy. **In a container it must bind
all interfaces**, because Docker forwards a published port to the container's
bridge address rather than its loopback:

```ts
await startHomeslateServer({ dataDir: "/data", hostname: "0.0.0.0" });
```

Keep the *host* side of the port mapping on loopback (`-p 127.0.0.1:8787:8787`)
so binding `0.0.0.0` inside the container does not expose the API to the LAN.

## Routes

`/api/displays` (GET/POST) and `/api/displays/:id` (GET/PUT/DELETE);
`/api/public/:publicId` (GET/PUT); `/api/display-calendar` (GET);
`/api/google/connect|callback|session` (GET); `/api/commute` (GET);
`/api/weather/alerts` (GET);
`/api/homeassistant/entities?domain=…` (GET);
`/api/homeassistant/states/:entityId` (GET);
`/api/homeassistant/todo/:entityId/items` (GET);
`/api/homeassistant/services/:domain/:service` (POST);
`/api/homeassistant/status` (GET);
`/` redirects to `publicBaseUrl`.

## Home Assistant transport

`/api/homeassistant/*` depends on a `HomeAssistantTransport`, not on `fetch`
directly. It is a generic three-method seam — `listEntities(domain)`,
`getEntity(entityId)`, `callService(domain, service, entityId, data, options?)`
— gated by the domain registry in `@homeslate/widgets/server`. Two
implementations ship:

- the built-in **direct** client, configured with `homeAssistant: { baseUrl, token }`;
- the **relay** transport from [`@homeslate/relay`](/docs/packages/relay),
  injected as `homeAssistant: { transport }` — for a hosted API that reaches a
  home Home Assistant through a [LAN agent](/docs/packages/agent).

Because the transport is domain-agnostic, adding a widget means adding a
registry entry (entity-id shape, allowed services, allowed data keys, optional
mapper) — the same entry drives the routes, the relay, and the agent. Validation
runs on all three, so an unknown domain, service, or data key never reaches Home
Assistant.

`GET /api/homeassistant/status` reports `{ configured, transport, connected,
haReachable }`, so a client can tell "not set up" from "agent disconnected":

| Situation | Status |
| --- | --- |
| No transport and no credentials | `501` |
| Relay configured, no agent connected | `503` |
| Relay configured, agent up, Home Assistant down | `502` |
| Relay request timed out | `504` |
